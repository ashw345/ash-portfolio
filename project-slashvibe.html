SlashVibe AI 控制面

给并行的 AI Agent 一个能用余光读懂的控制面——一块横屏、三颗按键、一根摇杆、一支可分离的麦克风。

客户是自然映射——已完成 A 轮融资的硬件团队，SlashVibe 是他们的首款 AI 控制面产品。创始人做了三年键盘，AI 改变工作方式之后，问题从「怎么打字更快」变成了「怎么更自然地指挥 AI」。我负责软件侧从 0 到 1 的全部体验：使用流程、按键映射、信息架构与界面设计。

Scope 这是一个 0→1 的项目，没有可参照的旧版本，硬件也在同步定型。我的工作从「人到底在为什么付出成本」开始，推导出三条原则，再用它们裁判后面每一个分歧——从层级要压到几层、四个动作各自落在哪一块界面，到状态该给几种颜色、选中态能不能发亮。视觉与界面全部由我完成。

PART 01 — UX 把问题想清楚
01Problem

Agent 越多，人越忙

开发者同时挂着 3–6 个会话，每一个都可能正在思考、已经完成、或者停在一个等你点头的岔路口。屏幕上没有任何一处能「扫一眼就知道」，于是人被迫轮询。被消耗的不是时间，是切换。

我的解法可以压成一句：把「查询」变成余光就能完成的动作，把「回复」降级成拨一下摇杆。

看不见状态
终端里「还在跑」和「已经停了」长得一模一样。
回复要打字
一个「继续」要抢回焦点、找窗口、输入、回车。
上下文断掉
换一个会话，等于把整个项目重新解释一遍。
FIG.01 — 一个回合里，人的时间去了哪
派发任务 8%
轮询各会话 54% · 要被压进余光
读结果 26%
下一步决策 12% · 真正属于人的部分

02Constraints

硬件先定，界面只能顺着它长

和工业设计同步推进，屏幕比例、按键数量、麦克风能不能分离，都会反过来改写界面。我把这三条依赖显式写下来，双边才好同时改。

真机一放上桌，手机习惯先被推翻：屏很矮、字很大、离眼睛更远，而人根本不会一直盯着它。卡片、分组容器、滚动列表——全部要重新验证。

CONSTRAINT 01
屏幕横且矮
纵向预算极紧，容器和边框成了奢侈品。
CONSTRAINT 02
只有 3 键 + 4 向
不能新增输入，只能重新分配语义。
CONSTRAINT 03
麦克风可分离
语音要能在任何页面唤起，因此它不进层级。
FIG.02 — 使用条件对照
条件 手机 SLASHVIBE
注视方式 持续注视 余光扫视
屏幕比例 竖向可无限滚动 横向且矮，行数有限
字号 小字近看 大字远看，被视距锁死
输入 指到即选 只有上下左右
分组方式 用容器 用间距与颜色

现场验证得到的三个结论：颜色比文字先到达；屏效等于信息密度；夜间是常态工况。

03Principles

三条原则，后面所有分歧都用它们裁判

P—01
余光感知
状态由颜色承担，内容由白字承担。不读字也能判断要不要现在管它。
P—02
手不离位
同一方向在任何页面语义一致：上下选择、右确认、左返回。可预测比可发现重要。
P—03
屏效优先
任何视觉元素都要用「它挤掉了几行任务」来结算。
04Task Loop

任务循环使用流程

一个回合：从口述到点头，手不离桌。下面先看五步的骨架，再看完整状态机——WAITING / READY / ERROR 三条分支最终都汇回同一个语音输入口。

FIG.03 — STEP 2 · WORKING
FIG.04 — STEP 3 · WAITING ON YOU
STEP 1 口述派发 按住语音键说完需求，文字落进当前会话，不抢键盘焦点。 语音键
STEP 2 回到工作 屏幕转为 WORKING。蓝色低调不动，明确地说「现在不用管」。 WORKING

STEP 4 拨一下就决定 选项已预置为 A–E，下选、右发送。一次决策 = 两个动作。 ↓  THEN  →
STEP 5 收尾或纠错 绿色安静收尾；红色把堆栈直接呈现，不必回终端翻日志。 DONE / ERROR

框内可滚动 ↕

T0 开机到 T15 回到 WORKING 的完整状态机。颜色沿用产品自己的状态语言：黄 = 等你、绿 = 就绪、红 = 出错、蓝 = 在跑，紫 = 用户操作页，灰 = 系统自动事件。

05Key Mapping

三颗键、四个方向，覆盖全部操作

映射表先写完，界面再画——界面必须长成映射表的样子，而不是反过来让操作去迁就画面。

可分离控制器：左起三颗按键（取消 / 发送 / 语音），右侧一根四向摇杆。全部操作只能落在这五个输入上。

输入 MISSION BOARD TASK WINDOW VOICE
↑ ↓摇杆 上/下 切换任务行 在选项 / 历史间移动 —
→摇杆 右 进入该会话 确认并发送当前选项 结束录音并发送
←摇杆 左 已在顶层 返回 Mission Board 放弃本次录音
⏎发送键 对选中会话直接继续 发送 结束并发送
⊘取消键 消除该行提醒 中断当前生成 丢弃
〜语音键 对选中会话口述 对本会话口述 按住说话 · 松开预览

方向语义三处不变。右永远是往前一步，左永远是退一步——包括在语音层里，右是发送、左是放弃。

按键与摇杆有意重叠。发送既能按键也能拨右——手在哪就用哪个，不必先低头找。

PART 02 — UI 把界面做出来
06Anatomy

Mission Board 版式解剖

左列固定宽度只放状态词，右列放内容——两列一刀切开，颜色在余光里连成一条竖带。人扫过去看的是「有没有黄和红」，而不是逐行阅读。

状态词 等宽大写，宽度稳定，不随语言变长。
标题 始终白色。可读性不参与状态编码，避免彩色正文。
选中态 描边加微光，不用填充色块——夜里不刺眼。
顶栏 模型、额度、消耗常驻，不为查用量再开一层。
行高 按视距反推最小字号后再定行高，保证一屏排得下六行。
07Decisions

两个决策，都是用原则判出来的

决策 01

列表页：把要求写成判据再筛

这一屏画了很多版。最后不是靠「哪个好看」选出来的，而是把三条要求变成能判 PASS / FAIL 的句子。

判据 01
余光感知
不看屏也要察觉有事发生——颜色够明显、位置固定。
判据 02
高易读性
任务标题一律白色。彩色标题在深色屏上牺牲阅读速度。
判据 03
屏效
矮屏上能排下的行数越多，「一览」才成立。
彩色标题 · 无状态列
卡片 · 状态徽标
纯文字 · 图标状态
状态色列 + 白色标题 · 采用
FIG.07 — 候选方案筛选
候选 余光 易读性 屏效 结论
彩色标题 · 无状态列 PASS FAIL FAIL 读得慢
卡片 · 状态徽标 FAIL PASS FAIL 行数不够
纯文字 · 图标状态 FAIL PASS PASS 余光看不见
状态色列 + 白色标题 PASS PASS PASS 采用

关键取舍：把颜色和文字的职责彻底分开。颜色只编码状态，文字只承载内容——两者不再互相牺牲，判据才能同时通过。

决策 02

默认就有一项被选中，所以选中态不能亮

最初用亮色填充按钮做选中。但进入页面时默认已选中第一项，等于深夜里迎面一块高亮色块。

BEFORE未采用
ALLM Reasoning Capabilities Meta
BHead out to handle errands
夜间刺眼；默认态看起来像「已确认」；与列表页的选中语言也不一致。
AFTER定稿
ALLM Reasoning Capabilities Meta
BHead out to handle errands
选中 = 描边发光，确认 = 摇杆右。与 Mission Board 用同一套选中语言。
08Screens

详情页展示

同一套骨架跑完全部状态：顶部状态条、中部内容、底部动作提示——结构不变，状态只改颜色。从任何一屏切到另一屏都不用重新找位置。

Retrospective

复盘与待验证

如果重做，我会更早把界面搬到真机上——前两周的稿子几乎全部因为视距和字号被推翻，这个成本本可以在第三天就付掉。

也会把状态语义先写成一页规格再画图。状态是这个产品的地基，我却是在画到第三屏时才把它抽象出来。

上线后想验证

WAITING 出现到用户响应的时间——「余光感知」是否成立的唯一硬指标。

A–E 预置选项的采纳率，以及「Others 回桌面输入」的触发比例：它决定语音层要不要再往前一步。
